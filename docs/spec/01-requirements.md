## 1. 배경·목표
- 개인 X 계정(최대 3개)의 과거 게시물을 전량 또는 조건부 삭제. 계정 정지 위험을 0에 가깝게 → 속도보다 안전
- 부수 목표(우선순위): ① 계정 안전 ② 최신 개발 방법론·자동화 파이프라인 학습 ③ LLM 내부 원리 ④ 웹/서버/CS 기본기 ⑤ 확장 가능 구조 ⑥ 기술 블로그 소재
- 성공 기준: 대상 100% 삭제 · 계정 경고/잠금 0회 · 총비용 상한 이내 · 다른 Windows PC에서 clone 후 재현

## 2. 범위
### 포함
- 실행 단위 = 로그인 계정 1개 + 그 계정의 아카이브 폴더 1개. 계정은 사전 등록 없이 실행 시 지정 **[확정]**
- 아카이브(`tweets.js`) 파싱 → 로컬 인벤토리 → 분석 보고서(`analyze`)
- 필터(전체/기간/키워드/유형/보존) · 계획(`plan`, dry-run) · 삭제 실행(`run`) · 감사 로그 · 보고서
- 대상 유형 v1: 원글, 답글, 미디어 포함 게시물 **[확정]**
- 로컬 웹 대시보드(2단계) **[확정]**
### 제외 (v1) — 액션·필터 확장 지점으로 예약
- 리포스트 취소(`unretweet`) **[확정: 기본 제외, 추후 필터·액션 플러그인으로 추가]**
- 좋아요 취소 · 북마크 · DM · 팔로우 정리 · 타인 게시물 · 서버 호스팅
- 브라우저 자동화 경로 일체(헌장 P1)

## 3. 환경·전제
- 실행 PC: Windows 11 Home · Python 3.14.7 · Node/Docker/WSL 없음(2026-09-17)
- 계정 규모: 합계 약 1만~3만 건 **[확정, 정확한 수치는 `analyze`로]**. 계정별 아카이브 zip 보유 **[확정]**
- 아카이브 배치: `data/<계정명>/` 아래 zip 또는 해제 폴더. `data/`는 gitignore. 프로그램은 `tweets.js`(+검증용 `account.js`)만 읽고 DM 등 다른 파일은 열지 않음 **[확정]**
- X Developer 계정 1개 + 앱 1개로 3계정 모두 OAuth 인증 가능. 종량제 크레딧 최소 $5
- 아카이브 시점 이후 게시물은 대상에서 빠짐 → 마무리 단계에서 owned-read(≤3,200건, $0.001/건) 보충 **[제안]**

## 4. 기능 요구사항
| ID | 요구사항 | 상태 |
|---|---|---|
| FR-01 | OAuth 2.0 PKCE 로그인(localhost 리다이렉트). 토큰은 OS 자격증명 저장소에 계정 id별 저장. access 2h 자동 갱신, refresh 6개월·1회용 회전 | 확정 |
| FR-02 | 아카이브 zip/폴더의 `tweets.js`(+`tweets-part*.js`) 파싱 → SQLite 인벤토리(id·시각·텍스트·유형·답글 대상·미디어·지표) | 확정 |
| FR-03 | 유형 분류: 원글 / 답글(`in_reply_to_status_id`) / 리포스트(`RT @` 접두) / 미디어 포함(`extended_entities`) | 확정 |
| FR-04 | 필터 파이프라인: 전체 · 기간 · 키워드/정규식 · 유형 · 보존 목록(id·고정글) · 지표 임계(좋아요·리포스트 ≥ N 보존). 조합 가능. 파일 1개 추가로 새 필터 등록 | 확정 |
| FR-05 | `analyze`: 유형별 건수 · 연도별 분포 · 미디어 수 · 예상 비용($0.005/$0.010 두 시나리오) · 프리셋별 예상 소요를 MD/CSV 보고서로 출력. 첫 산출물 | 확정 |
| FR-06 | `plan`: 필터 결과를 표·CSV로 출력(건수·예상 소요·예상 비용). 기본 명령 = dry-run | 확정 |
| FR-07 | `run`: 명시 플래그 + 확인 후 삭제. §6 페이싱 강제. Ctrl+C 안전 중단, 재실행 시 이어서 | 확정 |
| FR-08 | 응답 처리: 200 `deleted:true`→완료 · 404→이미 없음(완료) · 429/401/403/5xx→§6 회로차단 | 확정 |
| FR-09 | 액션 인터페이스: v1은 `delete_post`만 구현. `unretweet`·`unlike`는 같은 인터페이스로 추후 추가(엔드포인트·단가·한도만 다름) | 확정 |
| FR-10 | `status`/`report`: 진행률·성공/실패/잔여·누적 비용·다음 실행 가능 시각. 세션 종료 시 요약 파일 | 확정 |
| FR-11 | 감사 로그(JSONL): 항목별 요청 시각·응답 코드·`x-rate-limit-*` 헤더 | 확정 |
| FR-12 | 설정(TOML): 페이싱 프리셋·활동 시간대·일일 상한·비용 상한. 하드 상한 초과값은 기동 시 거부 | 확정 |
| FR-13 | 삭제 전 스냅샷: 텍스트·메타를 DB에 보존, 미디어는 아카이브 내 원본 경로 기록 | 확정 |
| FR-14 | 검증 샘플링(선택): 완료 항목 일부를 owned-read($0.001)로 실제 삭제 확인 | 제안 |
| FR-15 | 계정 단위 상태 분리: 토큰·DB·로그를 인증된 사용자 id로 자동 분리. 사전 설정 불필요. 동시 실행 1개 | 확정 |
| FR-16 | 아카이브-계정 일치 검증: 아카이브 `account.js`의 accountId와 `GET /2/users/me` id가 다르면 실행 거부 | 확정 |
| FR-17 | 로컬 웹 대시보드(FastAPI+HTMX): 진행률·로그·설정. 2단계 | 확정 |
| FR-18 | LLM 분류 필터(주제·톤 기준 보존/삭제 추천, 사람이 최종 승인) | 제안(v2) |

## 6. 안전 정책 (수치)
- 공식 한도(2026-09, 사용자 단위): `DELETE /2/tweets/:id` 50/15min · `GET /2/users/me` 75/15min · (확장용) `DELETE retweets` 50/15min · `DELETE likes` 50/15min + 1,000/24h
- 페이싱 프리셋 **[제안]** (활동 시간대 14h 기준)

| 프리셋 | 건당 간격(무작위) | 15분 사용률 | 시간당 | 일일 | 1만 건 | 3만 건 |
|---|---|---|---|---|---|---|
| `cautious`(기본) | 90~180s | ≈13% | ≤30 | ≤300 | ≈34일 | ≈100일 |
| `normal` | 40~80s | ≈30% | ≤60 | ≤800 | ≈13일 | ≈38일 |
| `brisk` | 20~40s | ≈60% | ≤120 | ≤1,600 | ≈7일 | ≈19일 |

- 권장 운영 **[제안]**: 첫 주 `cautious`(워밍업: 첫날 ≤50건, 3일간 상한 50%→100%) → 이상 없으면 `normal`. `brisk`는 사용자 명시 시만
- 활동 시간대 로컬 09:00~23:00 **[제안]**. 세션 최대 3h 후 30~60분 휴식
- 회로차단: 429→창 reset+여유 대기, 세션 내 2회면 종료 · 401/403→즉시 종료+알림(사람 확인) · 5xx→지수 백오프(30s→15min), 3연속 종료 · 응답에 잠금/제한 문구→종료
- 하드 상한(코드 고정): 15분 ≤30건 · 일일 ≤1,600건. 설정으로 초과 불가
- 읽기 최소화: 열람은 아카이브. `GET users/me` 세션당 1회(FR-16 검증 겸용). 검증 샘플링 선택
- 계정 간 순차 실행. 한 PC·한 IP에서 여러 계정을 동시에 돌리지 않음

## 7. 제약·가정
- X API: 2026-02 무료 티어 폐지, 종량제만. 가격·정책 변동 가능 → 비용 상한 필수
- API 열람은 최근 3,200건 + 유료 → 전체 열람은 아카이브만
- 삭제 요청 단가 카테고리(`Content: Manage` $0.005 vs `Interaction: Delete` $0.010)는 공식 페이지에 엔드포인트 매핑 없음 → 개발자 콘솔에서 확인. RT 취소는 후자일 가능성 높음
- 아카이브에는 DM 등 민감 데이터 포함 → 프로그램은 필요한 파일만 읽고, 아카이브를 저장소·채팅에 올리지 않음
